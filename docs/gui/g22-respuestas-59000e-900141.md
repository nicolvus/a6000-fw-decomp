# G22 — Respuestas para `0x59000e` (VDF) y formato de `0x900141` (fecha) (12-11-2026)

Análisis estático con `llvm-objdump` de fw 3.21 (`nflasha15_unpacked_unpacked/lib`): `libObj.so` (md5 `eb12512e…`), `libBizFw.so` y `dataflowInfraFramework.so`. Sin VM ni REA. Especificación para el agente del arnés; no toca `sonyshim.c`.

## 1. `0x59000e` es el servicio VDF (pantalla), y la espera no es un bucle

**Quién llama (VERIFICADO).** `ObjRenderer SequenceAppChangePositionCmd` (`libObj` `0x2aed94`, cadena «In» en `0x2aedc6`) llama, en este orden, a métodos de `OBJAVBBCBASECLASS::VdfCh` (`libBizFw.so`): `getPanelOut` (`0x2aef42`), `getBlackFrame` (`0x2aefba`), `getOSDLayout` (`0x2af0ba`) y, según el caso, otros. Cada método arma una petición y llama a `DataflowInfraCh::sndRcvAsyncDataflowMsg(rsp, rsp_len, req, req_len, ?, dest, timeout)` (`libBizFw` `0x35378`) con **`dest = 0x59000e`** (literal `0x37afc` en `getPanelOut`, `0x3b03c` en `getBlackFrame`) y `timeout = 0xffffffff`.

`sndRcvAsyncDataflowMsg` = `allocOsalId` (cola de respuesta propia, p. ej. `0x2940d4`) → `sndAsyncDataflowMsg` (MsgSnd) → **un solo** `rcvAsyncDataflowMsg` (MsgRcv) → `DataflowInfraReceiver::ReceiveASync` (`dataflowInfraFramework.so` `0x1b968`) → `DataflowInfraMsg::GetMsg` (`0x1a984`). No hay bucle: si tras una respuesta «vuelve a esperar», es **la siguiente llamada VDF** (otra orden) a la misma cola, que también necesita respuesta.

**Petición (VERIFICADO por los `strh`).** Cabecera de 8 B dentro del mensaje: `u16 0x2001` (categoría VDF), `u16 orden`, `u16 longitud`, `u16 1`, y los parámetros. Las usadas por el renderizador:

| Método | Orden | Long. pet. | Tamaño respuesta | Resultado (debe ser 0) |
|---|---|---|---|---|
| `getPanelOut` | `0x10b` | 8 | 0x10 | `rsp+0x0c` (u32) |
| `getBlackFrame` | `0x310` | 0x0c (+1 B parámetro) | 0x18 | `rsp+0x14` (u32) |
| `getOSDLayout` | `0x308` | 8 | 0x10 | `rsp+0x0c` (u32) |

Todas las órdenes de `VdfCh` (todas con espera síncrona salvo `setPanelColor 0x104`, que no espera): `0x100–0x115` (pantalla), `0x200–0x211` (servicio), `0x300–0x315` (entrada/OSD), `0x400/0x401` (ruta).

**Clasificación de la respuesta en `ReceiveASync` (VERIFICADO, `0x1b984–0x1ba02`).** Lee el mensaje con `osal_rcv_msg_tmo`; `MSGID = [msg-4]`; copia `min(osal_msg_size, 0x100)` bytes del cuerpo.
- Si `MSGID` ∈ {`0xc2019f`, `0xc20219`, `0x61003c`, `0x1590438`} → **tipo 2** (bruto).
- Si no, y `cuerpo+4 == 0xa0a0a0a0` → **tipo 1** (contenedor dataflow).
- Si no → **tipo 2**.

`GetMsg`:
- **tipo 2**: `memcpy(rsp, cuerpo, min(tamaño, rsp_len))` → éxito.
- **tipo 1**: necesita `u16 cuerpo+8` (número de elementos) ≠ 0 (si 0 → error `-0x1b`), `u32 cuerpo+0xc` = desplazamiento del elemento, y en el elemento `u16 +4` = longitud ≤ `rsp_len` (si mayor → error `-0x1c`); copia el elemento. Probable motivo de que la respuesta «comp» al estilo ObjMic no sirviera (NO_VERIFICADO: no se tiene el contenido exacto que se envió).

**Respuesta mínima recomendada (por cada mensaje recibido en `0x59000e`):** enviar a la cola de origen (la de `allocOsalId`, `0x2940d4` en la traza; es el `src` del mensaje/primer `u32` del cuerpo de la petición) un mensaje **tipo 2**:
- `MSGID` cualquiera ≠ los cuatro anteriores (vale `0x8200`);
- cuerpo de **0x40 bytes a cero** (cubre todos los `rsp_len` usados ≤ 0x18 y deja el resultado en 0), opcionalmente con la cabecera de 8 B de la petición copiada en `+0` (no la comprueba nadie);
- `cuerpo+4` **no** puede ser `0xa0a0a0a0`.

Con ceros, `getPanelOut`/`getOSDLayout` devuelven tamaños 0; el renderizador solo los compara con los anteriores (`0x2af01e–0x2af04c`) y reconfigura si difieren. NO_VERIFICADO que eso no provoque otra espera o un dibujo vacío; si ocurre, rellenar `getPanelOut` con el tamaño del panel (campos u16 en `rsp+0…+0xb`, orden no decodificado).

## 2. `0x900141` no es el aviso de cambio de fecha: es el servidor de fecha de `libObj`

Callback `libObj+0xb58be8` (VERIFICADO). Mensaje de 0x16 B:

| Offset | Tipo | Uso |
|---|---|---|
| `+0x00` | s16 | orden 0–5 (`tbh` `0xb58bfc`); > 5 → error |
| `+0x02` | s16 | **resultado**, escrito por el callback (0 = bien; error `[0xb58e54]`/`[0xb58e58]`) |
| `+0x04` | u16 | año (orden 3: `Backup 0x90000e` (2 B) + `Backup 0x90000f` (1 B)) |
| `+0x06` | u8 | `Backup 0x900008` |
| `+0x07` | u8 | `Backup 0x900004` |
| `+0x08` | u8 | `Backup 0x900006` |
| `+0x09` | u8 | `Backup 0x900007` |
| `+0x0a` | u8 | `Backup 0x900009` |
| `+0x0c` | s16 | 3 → sin fecha (puntero nulo) en órdenes 0/1/4/5; la orden 3 lo pone a 0 |
| `+0x0e` | 2 B | `Backup 0x90000a` (2 B) |
| `+0x10` | 2 B | `Backup 0x900005` (2 B) |
| `+0x12` | s16 | 1 → sin `+0x0e` en órdenes 0/1/4/5; la orden 3 lo pone a 0 |
| `+0x14` | u16 | argumento de las órdenes 0/1/4/5 |

Órdenes:
- **3** = leer fecha de la NVRAM. Cada `Backup_read` debe devolver el tamaño indicado (2 o 1); si no, error y traza (`0x90`).
- **0/4** = `0xb59fa0(fecha, +0x0e, +0x14, 0/1)`.
- **1/5** = `0xb586e4(…)`. Ambas leen y comparan NVRAM; probablemente sean escritura de fecha o huso con o sin verano, NO_VERIFICADO.
- **2** = no hace nada (resultado 0).

Qué hace falta para que Fecha/Hora muestre la hora:
1. que el shim **entregue** a este callback los mensajes a `0x900141`, igual que con `0x90013e`, en lugar de descartarlos;
2. que el `Backup_read` del shim (NVRAM real) devuelva **2 B** para `0x90000e`, `0x90000a` y `0x900005`, y **1 B** para `0x90000f`, `0x900008`, `0x900004`, `0x900006`, `0x900007` y `0x900009`.

Qué campo es mes, día, hora o minuto: NO_VERIFICADO. La correspondencia de offsets es directa, pero no se cruzó con los valores reales de la NVRAM. Con una NVRAM leída en cámara se comprueba en un paso.

El **aviso** de cambio (`osal_reg_datechg_notify_cb`) sigue sin localizar. No hace falta para pintar la página si esta consulta la fecha por `0x900141` (orden 3), pero eso es NO_VERIFICADO: no se trazó qué orden envía la página.
