# Productor del YC de SFRA y condiciones de operación (línea F, Claude; parcial)
Ver además `sfra-linux-client.md` (ISS→buzones, DMM, propiedad).
- VERIFICADO (cadenas + decompilado): SFRA no «tira» del sensor: recibe YC por **pines** de un sistema «SFRS» (`SystemCmdPinConnect/Disconnect/Get/RequestConnect/RequestDisconnect/PinSend`). `PinSend` (función `0x439abbfe`, export `sfra-pinsend.json`) manipula objetos pin con contadores (`GetCounter`, `nowVfc`, `osalID`, `Handle`) y registra «Send **RecPin**» (grabación) y «Send **EEPin**» (EE = visor/Live View); emite un mensaje `0x2009/0xb012` (longitud 0x28, handle de pin, índice de path) hacia el siguiente eslabón y libera el YC con `FUN_43b63566(handle,-1,-1)`.
- VERIFICADO: existe un modo «**shutter mute thru**» (`0x439ac2fa`..., cadena `0x43ce955e`) y «kari review thru/free»: durante el apagón de obturador/revisión rápida, SFRA decide si deja pasar (thru) los fotogramas según una máscara de tipo de fotograma (`0x20`, `0x01`, `0x30/0x31`).
- VERIFICADO: el JPEG se produce en SFRA con YC recibido por pin; `GET_JPEG` solo recoge READY (ver otros documentos). La entrada YC real viene del flujo EE/Rec del sistema de imagen (ADF: `DefDataflowInfraPin.h`).
- INFERENCIA: por tanto el productor del YC es el pipeline de vídeo/EE (DFE/CamCore → ADF pin EE) y SFRA depende de que el path esté abierto (`SET_PATH(OPEN)`, ISS lo hace con anchos 320/640/1024) **y** de que haya LV activo; no depende de una captura fotográfica ni emite CAIF.
- NO VERIFICADO: quién emite `SystemCmdPinConnect` para EE en modo foto sin Wi-Fi; si el path se puede abrir localmente (libObj tiene `ObjScalar::SequenceSfrSetPathJpegCmd`/`SequenceSfrFuncGetJpegCmd`/`SequencePin{Open,Connect,Deliver,Notify}`: ver `sony-dcf-playback.md`, sugiere que **libObj sí puede abrir el path y pedir JPEG** como cliente interno vía ScalarDaemon); exposición del frame (probablemente la de LV); resoluciones >1024 vía ISS.
